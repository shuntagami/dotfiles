# 説明・操作動画の制作と編集

台本と素材を場面単位で管理し、修正時に必要な部分だけ作り直す。MulmoScriptは制作の正本にし、動画化は目的に合うエンジンを選ぶ。付属スクリプトはローカル画像・動画・音声を扱うFFmpeg実装で、MulmoCast CLIを実行したことにはしない。

## 依頼に合う方法を選ぶ

- **新しく作る**：目的に沿って構成・素材・音声を用意する。継続して直す動画は、[制作形式](references/project-format.md)に沿って場面ごとに管理する。
- **制作済みの内容を変える**：元のプロジェクトがあれば、変更する場面を直す。変わらない映像・音声・字幕を再利用し、最後に全体をつなぎ直す。
- **完成動画を加工する**：カット、結合、倍速化、音量調整、縦長化、字幕・テロップ追加などは、[既存動画の編集](references/editing-existing-video.md)を読む。単純な加工のためにMulmoScriptのプロジェクトを新設したり、ナレーションを生成し直したりしない。

依頼が具体的なら、そのまま必要な作業を進める。手段や工程数は素材と目的に合わせて選び、構成案や試作の確認を毎回必須にしない。判断で内容が大きく変わる点や、利用者が確認を求めた点を相談する。

## まず成果物を特定する

会話と既存ファイルから、視聴者、動画の目的、現在の運用、変更点、必要な操作、納品形式を把握する。既に決まっていることは聞き直さない。

- **単体解説**：前の動画を見ていなくても意味が通る導入と締めを持たせる。
- **操作本編**：開始から完了確認まで、視聴者が実行する仕事を扱う。
- **補足・接続パート**：本編固有の前提や移行方針を説明する。
- **結合確認版**：複数素材をつないだ試作。本編が欠けている場合、完成版として扱わない。

素材の役割と含む内容を `video-plan.json` の `kind` と `coverage` に残す。「操作フローを送って」と言われたら、入門＋補足だけの動画を選ばない。納品時にタイトル・内容・バージョン・検証済みファイルを対応付ける。

## 構成から制作へ

構成確認を依頼されたときは、章順・説明の要旨・見せる操作が分かる案を先に作る。構成の方向が承認されたら、特段の指示がない限り本編の完成まで進める。試作だけを完成として納品しない。

各beatに安定した `id` を付け、`text` を読み上げ原稿、`image` / `audio` を素材参照にする。独自の編集情報はMulmoScriptへ混ぜず、別の `video-plan.json` に置く。最小例とコマンドは [制作形式とスクリプト](references/project-format.md) を読む。

## 説明の組み立て

初心者向けの本編は、達成する仕事と仕組みの目的を短く説明し、全体の流れを示してから実操作へ進む。用語の暗記や設定名から入らない。操作だけの短い切り出しを求められた場合は、導入を膨らませない。

- **用語は具体的な働きで説明する。** 「誰が、どのサービスの、何を取得・変更できるようになるか」を示す。「AIが見る窓口」のように、短い比喩だけで接続先や用途を省かない。製品名を勝手に短縮しない。
- **通常画面からの道順を見せる。** 設定や確認画面を突然出さず、入口のボタン → メニュー → 対象画面 → 操作結果を追える映像にする。ショートカットを使う場合も、どこから何を開いたかを伝える。画面名・項目名は収録時の実UIで確かめる。
- **操作する人と反映のタイミングを区別する。** 視聴者、AI、クライアントなどの担当を明示する。代理ログインで見えるボタンでも、相手側が行う承認・確認を撮影者の完了操作にしない。相手の操作を理解すれば足りる場面は、その役割と結果を説明する。
- **採用した手順を一本の流れにする。** たとえばAIに修正とPR作成を任せる運用なら、人が手動でcommit・pushする別案を途中に混ぜない。比較を求められた場合は別の説明として扱い、現在の運用と将来案も区別する。
- **本編固有のつまずきに尺を使う。** 接続、画面への入口、反映の契機、役割の違いを優先する。「問題がなければ進む」「確認が必要なら保留」といった自明な判断の繰り返しや、文章の細かな修正例は簡潔にする。通常の導入で不要なバージョン番号、制作中のトラブル対処、やり取りの枝葉は制作記録へ回す。

本編の前に済ませる承認・反映などは、開始条件として短く補足する。本編の対象外なら操作実演を足さない。画面やAIの取得結果で確認できる情報を、収録の都合だけで別の要約ファイルへ転記する手順も追加しない。

AI連携の接続確認と、指摘を構成へ反映する方法は [台本の直し方](references/recording-and-revisions.md#台本の直し方) を読む。

## 映像の選択

- 概念や目的の説明は、人物・原稿・道具など具体物の図解が伝わるかを考える。このユーザーの説明動画では、生成画像の図解を基本候補にする。画像生成が適切なら利用可能なimagegenスキル／ツールを使い、プロンプトと選定画像をプロジェクトへ保存する。
- 実際の操作は実画面やアプリの画面部品を優先する。画像生成した画面を、正確な実アプリのスクリーンショットとして扱わない。
- 操作再現を使う場合は画面内と制作記録に明記し、手順・結果を実装や隔離した検証環境で確かめる。架空データを使い、撮影のために本番通知や公開を実行しない。
- 複雑な入れ子の四角だけで初心者へ説明しようとしない。ただし図形やHTML自体を禁止せず、内容とユーザーの指定に合わせる。

録画・同期・素材再利用の注意点は [操作映像と変更管理](references/recording-and-revisions.md) を参照する。ブラウザやデスクトップの操作が必要なら、その環境で利用可能な操作スキルに従う。このスキルは操作制限を迂回する許可にならない。

## 音声・字幕・書き出し

既存音声を使える場合は再利用する。新規音声は、指定がなければ今回の既定候補としてOpenAI `gpt-4o-mini-tts` / `marin` を使える。ユーザー指定を優先し、モデルを変更する場合は現行の対応状況を確認する。

付属の `scripts/speech.py` は明示実行時だけOpenAI APIへ送信する。キーは指定された環境変数か、使用が認められた設定ファイルから読む。特定のリポジトリや個人の認証情報をスキルへ埋め込まない。

`scripts/video.py` は入力検査、音声に基づく時間割り、ローカル素材の映像化、字幕合成、検証、既存動画の結合を行う。対応外のMulmoScript表現は、素材を先に作るか、対応するMulmoCast CLIを使う。未対応の表現を勝手に簡易図へ置き換えない。

字幕は認識結果の誤字をそのまま出さず、元の台本にタイミングを対応付ける。音声が途中で終わった場合は、その場面だけ生成し直す。音声の尺やテキストが変わったら、その場面の字幕も更新する。

## 完成の確認と納品

進捗を伝えるときは、リハーサル・収録・編集・書き出し・アップロードのどの段階かを明記する。画面操作に詰まったら収録を止め、未完了の操作と不足している映像を具体的に伝える。

付属パイプラインで作った動画は `video.py verify` を使う。直接加工した動画は、実際の出力に対して尺・音声・再生可否と編集箇所を確認する。加工前の検証記録を加工後の動画の検証として流用しない。

操作の要所・文字の読みやすさ・最後の完了表示を完成動画で確認する。機械検証だけで操作の意味や事実の正しさを保証したことにしない。映像と音声の長さ、無音の混入、字幕の停止やずれ、単体版の独立性も見る。

元動画と制作素材を残し、指定された場所へ別名または別版で保存する。再生プレビューのツール（`showInPane` など）が使えれば表示し、無ければファイルへのリンクを渡す。プレビューの都合で保存先を勝手に変えない。

最終回答は、何が完成したか、再生先、尺、今回の変更点、重要な未完了項目を簡潔に示す。通常はエンコードの細部を並べない。
