# PR作成後に迷わず作業を続けるためのGit共通方針

## 目的

エージェントがPRを作ったあと、利用者が「この手元の変更は何か」「消してよいのか」を調べ直さずに、次の作業へ進めるようにする。また、利用者が見ているファイルと、エージェントが編集するファイルを一致させる。

この方針は全リポジトリで使う。ここでいう作業フォルダ（worktree）は、Gitのファイルが実際に置かれ、編集やアプリの起動に使われる場所のこと。

## 防ぎたい問題

### PRに出した変更が、元のフォルダでは未コミットのまま残る

例えば、次のような進め方で問題が起きる。

1. 元のフォルダAでファイルを編集する。
2. PR用に別のフォルダBを作り、編集したファイルをコピーする。
3. Bだけでcommit・pushしてPRを作り、Aの変更はそのままにする。

PRをマージしても、Aには「まだcommitしていない変更」が残る。Aでpullすると、Gitがその変更を上書きしないように止めることがある。自動同期も同じ理由で進まなくなり、利用者に後片付けが必要になる。ファイルには保存済みでも、Gitでは未コミットの状態だという点に注意する。

整理する対象は、**そのPRのために自分が元のフォルダへ残した変更**。別の作業で書いている途中の内容まで消してはいけない。

### 画面が表示する場所と、エージェントが編集する場所が分かれる

アプリや開発サーバーがAを見ているのに、エージェントがBへ移って編集すると、「直したと言っているのに画面が変わらない」状態になる。worktreeを作るだけでは、画面・保存先・チャットの作業場所は自動で切り替わらない。

## 作業するときの方針

### 編集を始める前に、作業場所を決める

- 対象リポジトリ、現在のブランチ、worktree、すでにある変更を確認する。シンボリックリンクの先が別リポジトリの場合もあるので、実体の場所を見る。
- すでにworkspaceを割り当てられている場合や、アプリがその場所を表示している場合は、そこで作業する。PRを作るだけなら、その場所でブランチを切ればよく、追加worktreeは必須ではない。
- 並行作業などで別のworktreeが必要なら、編集前に作る。途中で場所を変える場合は、画面や開発サーバーも同じ場所を使うか確認する。

### 編集後にPRを作りたくなっても、まず同じフォルダでブランチを作る

PRを作るためだけなら、場所は変えない。まだ作業用ブランチがなければ `git switch -c <作業ブランチ>` で作り、すでに今回の作業ブランチにいるならそのまま使って、その依頼の変更をcommitする。ファイルを別の場所へコピーしないので、元に未コミットのコピーを残す問題は起きない。

### 別のworktreeが必要なら、作業ブランチをcommitしてから移す

元のフォルダAで書き始めた変更を、別のフォルダBで続ける場合は、対象ファイルの変更がすべて今回の依頼に属することを確認してから、次の手順を使う。

1. 元のブランチ名を記録し、今回の対象ファイルを確定する。同じファイル内に他の作業の変更もある場合は、この移動手順を使わず、Aの作業ブランチで続ける。
2. Aで `git switch -c <作業ブランチ>` を実行する。元のブランチには、今回のcommitを積まない。
3. 今回の対象だけを `git commit --only -- <対象ファイル>` でcommitする。新規ファイルは先に対象を指定して `git add` する。`--only` は別ファイルのステージ済み変更をcommitに含めないが、指定ファイルの変更はすべて含むので、対象に他の作業を混ぜない。
4. Aを `git switch <元のブランチ>` で戻す。今回commitした変更はAのファイルから外れ、作業ブランチの履歴に残る。他の未コミット変更と衝突して切り替えを断られたら、強制せずここで止める。
5. `git worktree add <Bのパス> <作業ブランチ>` でBを開く。Gitがcommit済みの内容をBに展開するので、ファイルの手動コピーや削除は行わない。

**完了条件**は「Bに今回の変更がcommitとして揃っている」「Aは元のブランチに戻り、今回の未コミット差分が残っていない」「Aにあった別作業の変更は保たれている」の3つ。途中で止まった場合は、どこまで済んだかを報告し、移動完了とは扱わない。

同じファイルの一部だけを分ける場合、`--only` ではその部分だけを選べない。場所はAのままにし、PRへ出す差分を選別する。どの変更が今回の依頼か分からない場合は確認し、ファイル全体を戻したり、全変更をまとめてstashしたりしない。

この手順は、未コミットのコピーを作ってから後片付けするのではなく、**Gitの履歴に保存した作業を別の場所で開く**もの。stashを使う移動機能を選ぶ場合も、上の完了条件を満たすか確認する。対象ファイルを指定したstashでも別ファイルのステージ済み変更を移動先へ持ち込む場合があるため、部分移動が必要な場面に一律のstashコマンドを当てはめない。

参考：[git commit --only](https://git-scm.com/docs/git-commit#Documentation/git-commit.txt---only)、[git worktree add](https://git-scm.com/docs/git-worktree)。

### PRを作るときと、マージ後に確認する

- push・PR作成前に、作業先だけでなく、途中まで編集していた元のフォルダも確認する。開始時と比べ、自分の担当分が未コミットのまま置き去りになっていないことを確かめる。
- PR作成だけを頼まれた場合はマージしない。マージ・更新まで頼まれた場合は、GitHubの状態に加え、利用者が使うフォルダへの取り込みまで確認する。
- GitHubでのマージ後も、手元にはfetchと取り込みが必要。既存の自動同期や `sync.homeBranch` などの運用があればそれに従い、独自の同期処理を重ねたり、慣習だけで `main` にresetしたりしない。
- pullが止まったら、何の変更が残っているかを先に確認する。自動stashや強制resetだけで済ませず、PRに反映済みの内容と、まだ残すべき作業を区別する。

この文書はエージェントの作業方針であり、Gitの動作を変える設定や、Bash・worktreeの利用を一律に禁止する仕組みではない。使うのはGit標準の機能で、変更の所在と後片付けを明確にする。
