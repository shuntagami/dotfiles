# 普段のPRフローを保つためのGit共通方針

## 目的

エージェントに作業を頼んでも、普段どおり「作業ブランチで編集する → commit・pushしてPRを作る → 必要に応じてブランチを切り替える → GitHubでマージ・リモートブランチを削除する → ローカルに取り込む」という流れで進められるようにする。

利用者があとから「この手元の変更は何か」「消してよいのか」を調べ直す状態を作らない。この方針は全リポジトリに適用する。

## 防ぎたい例外的な問題

エージェントが元のフォルダで編集を始めたあと、PR用という理由で別のworktreeを作り、変更をコピーしてそちらだけでcommit・pushすると、元のフォルダには同じ変更が未コミットのまま残る。PRをマージしてもその状態は片付かず、pullや自動同期が止まる原因になる。

また、アプリや開発サーバーが元のフォルダを表示しているのに、エージェントが別のフォルダで編集すると、「直したと言っているのに画面が変わらない」状態になる。

ここでいうworktreeは、Gitのファイルが置かれている作業フォルダ。**同じフォルダでブランチを切り替えることと、別のworktreeへ作業場所を移すことは区別する。**

## 通常の作業

1. **今の作業場所で、今回の作業ブランチを使う。** 編集前にリポジトリ・現在のブランチ・既存の変更を確認する。まだ作業ブランチがなければ作り、すでにそのブランチにいるなら使い続ける。シンボリックリンクの場合は実体の場所も確認する。
2. **その場所で編集し、担当分をcommit・pushしてPRを作る。** PR作成のためにファイルを別フォルダへコピーしたり、途中でworktreeを増やしたりしない。PRを出すためだけに、作業ブランチを作り直す手順も挟まない。
3. **レビュー中のブランチ切り替えや修正は、普段の運用に従う。** 別の作業を始めるためにmainへ切り替えることも、PRの修正のために作業ブランチへ戻ることもできる。どちらも、同じ作業フォルダの中で行う通常の操作。
4. **マージ後は、普段の手順でローカルまで更新する。** GitHubでPRをマージし、リモートの作業ブランチを削除する運用ならそれに従う。ローカルでは既定ブランチへ切り替えてfetch・pullし、必要なブランチ整理を行う。既存の自動同期や `sync.homeBranch` が担う部分は、それに任せて結果を確認する。

PR作成だけを頼まれた場合は、マージやブランチ削除まで進めない。マージ・更新まで頼まれた場合は、GitHub上の完了だけでなく、利用者が使うフォルダへの取り込みも確認する。

## worktreeを追加するのは、必要な場合だけ

- 並行作業などで作業フォルダを分ける必要があるときに使う。毎回のPR作業には追加しない。
- アプリや利用者からすでにworkspaceを割り当てられている場合は、それを使う。さらにworktreeを作っても、画面・保存先・チャットが自動で追従するとは考えない。
- 新しいworktreeを使うと決めた場合は、できるだけ編集を始める前に用意する。
- **編集途中でどうしても別worktreeへ移す必要がある場合だけ**、[例外の移動手順](git-worktree-transfer.md)を参照する（`~/dotfiles/docs/git-worktree-transfer.md`）。その手順を通常のPRフローに組み込まない。

## 完了時に確認すること

- 担当した変更が意図したブランチ・PRに揃い、別の作業フォルダに未コミットのコピーを置き去りにしていない。
- 開始前からあった別作業の変更や、新規ファイルは保たれている。自分の作業の後片付けとしてまとめてcommit・stash・reset・cleanしない。
- pullが止まった場合は、PRに反映済みの内容と、まだ残すべき作業を区別する。自動stashや強制resetだけで済ませない。

この文書はエージェントの作業方針であり、Gitの動作を変える設定や、Bash・worktreeを一律に禁止する仕組みではない。Git標準の機能と、各環境で既に使っているPR・同期の運用を使う。
